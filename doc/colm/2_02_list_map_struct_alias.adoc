[[structs]]
== Structs

A struct groups named fields. `struct Name`, then its fields, each
`Name: Type`, then `end`, defines one:

[source,colm]
----
struct point
	X: int
	Y: int
end
----

A field can't have a first value: that is a parse error.

`new Name()` makes a struct, with its fields at 0, false or nil.
`new P: Name()` also declares `P`. `+P->Field+` reads or sets a field.
`P.Field` is an error, `dot cannot be used to access a pointer`.

A struct variable is nil until it is given a struct, so make one with `new`
before using its fields. Reading or setting a field of a nil struct stops the
program, as xref:8_04_error_handling.adoc#run-time-errors[the error handling
chapter] says. Assigning `nil` to a struct, list or map variable makes it nil
again. A field can't hold a struct of its own type, but it can refer to one
weakly, as xref:2_02_list_map_struct_alias.adoc#weak[weak references]
explain.

Structs are shared, as xref:2_00_types.adoc#sharing[the types chapter] says,
so a function can change a struct passed to it.

A struct can also hold `lex` blocks, tokens and defs. Passed to `parse`, it
is a parsing context, the subject of xref:3_04_undo.adoc#context[the context
chapter]. `context` is another keyword for `struct`.

[[aliases]]
== Aliases

`alias Name Type` gives `Type` a second name. The two names are one type, and
a value of either can be assigned to a variable of the other. An `alias` goes
at the top level, in a struct or in a namespace. In a function, it is a parse
error. `poker`, above, uses `alias` for its maps and lists, and `type_share`,
in xref:2_00_types.adoc#sharing[the types chapter], for a list.

[[lists]]
== Lists

`list<T>` holds values of type `T`, in order. `new list<T>()` makes an empty
one. A list's functions and fields are reached with `+->+`, as a struct's
are.

* `push_tail( V )` and `push_head( V )` add a value at the tail or the head.
  `push( V )` is `push_head( V )`.
* `pop_head()` and `pop_tail()` take a value off the head or the tail, and
  give it back. `pop()` is `pop_head()`. Popping an empty or nil list stops
  the program, as xref:8_04_error_handling.adoc#run-time-errors[the error
  handling chapter] says. Outside a parse's actions, a pop keeps nothing of
  what it took off, so a list used as a queue in a loop stays the same size.
  In a reduction or token action, or a function one calls, the parser keeps
  what a pop took off until the parser goes, at exit, so that backing up can
  put it back.
* `length` is the number of values.
* `for V: T in L` gives the values from head to tail, and
  `for V: T in rev_list_iter( L )` from tail to head.
* `head` and `tail` are the values at the head and the tail, and `top` is
  `head`. Reading one on an empty or nil list stops the program too. They
  can't be set or written through: `L->head = V` is `field "head" is const`,
  and `L->head.A = 1` is `left hand side qualification "head" is const`. To
  change an end, pop it and push the new value. A struct held at an end is a
  pointer, so `L->head->F = 1` sets its field.

A list can't change inside a `for` over it. A push or a pop in the loop's
body, on the local variable the loop is over, is a compile error,
`reference active, cannot write to object`. Any other push or pop while the
loop runs stops the program: one through another variable that holds the
list, in a function the body calls, on a global or a struct's field that the
loop is over, or in the actions of a parser that the body sends to. It
prints `fatal: changing a list a loop is over` and exits with status 1, as
xref:8_04_error_handling.adoc#run-time-errors[the error handling chapter]
says. A parser backing up over an action's push or pop while a loop is over
the list stops the program too, with
`fatal: backing up over a change to a list a loop is over`.

The variable of a `for` over a list takes each value as an assignment to it
would. Its type is `T`, or `any` when `T` is a tree type, or a tree type
when `T` is `any`. Any other type is a compile error, `loop variable V must
have the list's value type`, in a loop over `rev_list_iter( L )` too. Given
something that isn't a list, `rev_list_iter` is a compile error,
`rev_list_iter takes a list`.

The variable can't change either. Assigning to it is a compile error,
`cannot assign to V, the variable of a loop over a list or a map`, and so is
changing something inside it, as `V.A = 1` does: `cannot write to V, the
variable of a loop over a list or a map`. Nor can it, or anything inside it,
be given to a `ref` parameter, of a function or an iterator, or looped over,
as `for X: id in V` does: that is `cannot take a reference to V, the
variable of a loop over a list or a map`. Nor can it be yielded, as
xref:1_06_iterators.adoc#iterators[the iterators chapter] says. Copy it to a
local first, as `C: T = V` does, and use the copy. To change the values of
a list, build a new list of the changed copies. A list, a map or a struct
that the variable holds can still change, as `V->push_tail( X )` shows.

A list variable is nil until it is given a list, with `new`. Calling one of
a nil list's functions or reading one of its fields stops the program, and so
does a `for` over it, as a loop over a nil tree does
(xref:1_06_iterators.adoc#iterators[the iterators chapter]). A push prints
`fatal: push to a nil list`, a `for` prints `fatal: for loop over a nil list`,
and the program exits with status 1.

`argv` is a `list<str>`, as xref:1_00_language_overview.adoc#exit[the
language overview] shows.

[[maps]]
== Maps

`map<K, V>` maps keys of type `K` to values of type `V`. `new map<K, V>()`
makes an empty one. Its functions and fields are reached with `+->+` too.

* `insert( K, V )` adds the key `K` with the value `V`. If the key is there
  already, the map keeps its old value.
* `set( K, V )` gives the key `K` the value `V`: it adds the key if it isn't
  there, and replaces its value if it is. It gives 1 if it added the key, and
  0 if it replaced the value.
* `contains( K )` is true if the key is there, and false if not. It prints as
  1 or 0, as a comparison does.
* `find( K )` gives the key's value. When the key isn't there, it gives 0 for
  an `int` value, and nil for a `str`.
* `remove( K )` takes the key out, and gives its value, or nil or 0 if it
  wasn't there, as `find` does.
* `length` is the number of keys.
* `for V: ValueType in M` gives the values, in key order, and
  `for K: KeyType in map_keys( M )` gives the keys, in the same order.

Outside a parse's actions, a `remove` keeps nothing of what it took out, and
neither does an `insert` of a key the map has already, so a map that changes
in a loop stays the same size. In a reduction or token action, or a function
one calls, the parser keeps what a `remove` took out until the parser goes, at
exit, so that backing up can put it back, as it does for a pop.

Int keys go from low to high, negative ones first. Str keys go by length
first, then byte by byte, as xref:1_02_expressions.adoc#operators[the
expressions chapter] says.

A map can't change inside a `for` over it, or over `map_keys( M )`, in the
same way. An `insert`, a `set` or a `remove` there stops the program with
`fatal: changing a map a loop is over`, even one that would leave the map as
it was, such as an `insert` of a key the map has. A parser backing up over
an action's change to the map while a loop is over it stops the program with
`fatal: backing up over a change to a map a loop is over`.

The variable of a `for` over a map takes the values as in a loop over a
list. Any other type is a compile error, `loop variable V must have the
map's value type`. In a loop over `map_keys( M )`, the variable takes the
keys the same way: its type is `K`, or `any` when `K` is a tree type. Any
other type is a compile error, `loop variable K must have the map's key
type`. Given something that isn't a map, it is a compile error too,
`map_keys takes a map`.

The variable of a loop over a map can't change, be passed as a `ref`, be
looped over or be yielded either, as in a loop over a list.

A map variable is nil until it is given a map, with `new`. Calling one of a
nil map's functions, reading one of its fields or a `for` over it stops the
program the same way. An `insert` prints `fatal: insert into a nil map`, a
`for` prints `fatal: for loop over a nil map`, and the program exits with
status 1.

[[weak]]
== Weak references

A struct can't hold a struct of its own type, through a field of that type or
through what its fields hold: a list's or a map's values, a map's keys, a
parser's context, or a tree. An `any` can be given to a variable of any tree
type, so a field that holds a tree, a `str` included, counts as holding every
struct, list, map or parser that an attribute of a tree, or a `make_token`
argument, can hold. Colm refuses such a program when it compiles. The error is
at one of the places on the cycle, a struct's or a context's field if it has
one, and names the places that lead back to it. The route above, with
`Next: stop`, gives
`strong references make a cycle: stop.Next; declare a field or attribute in it weak`.

A place declared `weak<T>` refers to a value of type `T`, and doesn't count
toward a cycle. `T` is a struct, list, map, parser, `_input` or `stream` type.
Each cycle needs a weak place of its own: one elsewhere among the same types
isn't enough.

* It can be a struct's or a context's field, a variable, a parameter, a
  function's return type, a list's or a map's value, as in
  `list<weak<node>>`, or a def's or a token's attribute.
* It can't be a map's key, with the error `a map key can't be weak`, or a
  type that isn't a struct's, such as `weak<int>` or `weak<str>`, with
  `weak takes a struct type`. A host function's parameters and result can't
  be weak either.
* It reads as its value, or `nil`, and takes a `T` or `nil`. A loop over a
  list or a map of weak values has a `T` variable.
* A parser holds its context, so a context can't hold a parser of its own
  types: declare the field `weak<parser<T>>`.

For now colm frees a struct only when the program ends, so a weak place reads
as the value it was last given, or `nil`.
