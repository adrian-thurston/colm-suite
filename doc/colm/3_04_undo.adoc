[[context]]
= Context-dependent parsing

Some languages can't be parsed from their grammar alone. In C, `+a * b;+`
declares `b` as a pointer when `a` names a type, and is a multiplication
otherwise. `parse_order`, in xref:3_02_parse.adoc#parsing[the parsing chapter],
picks one of the two by the order of the productions. A C parser has to know
which names the typedefs it has read so far made into types.

In colm, the parse's own code collects such data, and uses it as the parse
goes on. Reduction actions write it, and token actions read it to decide
which tokens the parser gets. The data goes in a context, or in globals.

The parser backtracks, so actions run on alternatives that it later abandons.
Colm undoes what those actions did to the data.

This chapter covers context blocks, reading and writing the data, when
actions run, what backing up undoes, and `reject` with data.

== Context blocks

`context NAME`, then its contents, then `end`, defines a context. It holds
variables, each declared as a struct's field is, `Name: type`. It can also
hold `lex` blocks, defs, functions, iterators, structs and aliases.
Statements and `global` can't go inside a context: each is a parse error.

`context` is another keyword for `struct`, as
xref:2_02_list_map_struct_alias.adoc#structs[the structs section] says. A
context is a struct that holds a grammar. `new NAME()` makes an object of it,
and the program reaches its variables through the object, as in
`+Decls->Types+`.

A context object has one holder. A context can be the type of a local
variable, a parameter, a function's return and a variable of another
context, and of nothing else: not of a global, declared with `global` or
`export`, a field of a struct that isn't a context, a list's value, a map's
key or value, an attribute of a def or a token, or the `T` of a `weak<T>`.
Code that reached the object through one of these, as a function reaches a
global, could use it while a parser it was given can back up. Colm stops at
such a type with an error such as
`+G can't hold a ctx: a context object is held only by a local variable, a parameter, a return or a field of a context+`,
which names the global, field or attribute, or says `+a list's value+`,
`+a map's key+`, `+a map's value+` or `+weak<T>'s T+` in place of `G`. A
`context` with no def or token in it is a plain struct, and goes anywhere a
struct goes.

The variables start at 0, false or nil, as a struct's fields do. They can't
have a first value: that is a parse error. Make the lists and maps that a
parse uses before the parse:
xref:3_04_undo.adoc#context-lending[lending a context object] says when the
program can use the object.

Inside the block, code uses the context's variables, defs and tokens by
name. Outside it, the context's names are qualified as a namespace's are, as
in `decls::program`. xref:8_02_modularity.adoc#namespaces[The namespaces
chapter] covers qualified names.

A context's functions and iterators are qualified the same way outside it.
A context variable that one of them uses is the variable of the running
parse's context. If `decls` had a function `is_type( Name: str )` that looked
`Name` up in `Types`, `+decls::is_type( "a" )+` would look in the `Types` of
the object the running parse was given. So such a function works in the
actions of a parse given an object of its context, and in the functions they
call. Called outside a parse, or in a parse with no context or with an object
of another struct as its context, it stops the program where it uses the
variable, as xref:8_04_error_handling.adoc#run-time-errors[errors at run time]
do. A function that uses no context variable can be called from anywhere. A
call can't be given the object to use instead: `+Decls->is_type( "a" )+`
doesn't compile.

A parse of a type defined in a context is given an object of that context, in
parentheses after the type. These lines, from the example in the next
section, make the object and its map, and parse with it:

[source,colm]
----
Decls: decls = new decls()
Decls->Types = new map<str, str>()

parse Program: decls::program( Decls )[ stdin ]
----

A parser made with `new` is given the object the same way, as in
`+new parser<decls::program>( Decls )+`, which
xref:3_06_send.adoc#send[the send chapter] covers. The parse's actions use the
variables of the object it is given, so two parses given two objects keep
separate data.

Such a parse must be given its context. Colm doesn't compile a parse, or a
`new parser`, of a type in a context that is given none. Without
`+( Decls )+`, colm stops at the parse above with the error
`parsing decls::program needs a context of type decls`. A parse given an
object of another struct, or of another context, doesn't compile either. A
context variable that holds nil, given as the context, stops the program when
it runs, as xref:8_04_error_handling.adoc#run-time-errors[the error handling
chapter] says.

A def outside a context can name the context's defs and tokens in its
grammar, as `+def top [decls::program]+` would. A parse of `top` would run the
context's actions, which use the context's variables, but it can't be given
the context, since `top` isn't in it. A def in another context has the same
problem: its parse is given that other context. So colm doesn't compile a
parse, or a `new parser`, of a type whose grammar uses the defs or tokens of a
context other than its own, directly or through other defs. A literal counts
as a token of the context its lex block is in. A parse of `top` stops colm
with the error
`+top can't be parsed: its grammar uses decls::program, of context decls, and top isn't in decls+`.
The def can still be used where it isn't parsed itself: in the grammar of a
type in the context, whose parse is given the context, and in a `construct`.

In a token action written in a context, `this` is the parse's context, an
object of that context. The action uses the context's variables by name, or
through `this`, as in `+this->N+`. It can't assign to `this` itself:
`this = nil` is a compile error, `cannot assign to "this"`. A parse that the
action starts, of a type in the same context, must be given it, as in
`+parse_stop T( this input )[]+`. A parser made with `new` takes the context
alone, and gets its input from sends, so a parse of the action's input is a
`parse_stop` like this one. A parser made with `new` can be given `this` too.
It is lent the action's context until its `+finish()+`, and the action can't
use `this` or the context's variables until then, as
xref:3_04_undo.adoc#context-lending[lending a context object] explains. A
token action outside a context has no `this`.

A `global`, such as `HereEnd` in the example `lex_heredoc` in
xref:3_01_lex.adoc#lexing[the lexing chapter], can also hold data that actions
use, and it is undone in the same way. A context keeps the data with the
grammar that uses it, and gives each parse its own. The actions of a parser
that the program sends to can only read a global:
xref:3_04_undo.adoc#restartable[globals in a restartable parser] says why.

== When actions run

A reduction's action runs when the parser reduces. The parser reduces only
when it has the token after the production, as
xref:3_06_send.adoc#send[the send chapter] says too. By then, that token has
been scanned, and its token action has run. So a token action sees what a
reduction's action wrote only from the second token after the production.

In `ctx_typedef`, `new_type` ends before the `;`. Its action runs when the
parser has the `;`, before the first name of the next statement is scanned.
Here the insert is moved into the action of the statement instead, and
`new_type` has no action:

[source,colm]
----
def statement
	[`typedef type new_type `;]
	{
		Types->insert( $r3, $r3 )
	}
|	[type `* name `;]
|	[name `* name `;]
----

That action runs only when the parser has the token after the `;`: the first
name of the next statement, which has already been scanned as a `name`. With
the example's input, the third line would print `+multiplication: a * b;+`.

Put a write in the action of a production that ends at least one token before
the first token that needs it.

`a b;` could begin an assignment, so the parser first takes `a` as a
`target`. The action prints `target: a`, and adds `a` to `Assigned`. At the
`;` there is no `=`, so the parser backs up, and takes the second production
of `statement`. Backing up over the reduction of `target` undoes its action:
`a` comes off the list. What the action printed stays printed.

When the parser backs up over a reduction, colm undoes what the reduction's
action did to the data. When it backs up over a token, colm undoes what the
token's action did. The token's text is then scanned again, and the action
runs again, with the data as it is then.

Colm undoes:

* assignments to the variables of a context and to globals, and to the fields
  of the structs they hold
* writes into the trees those variables hold, at any depth: setting a child,
  a token's text, or an attribute that holds a tree or a `str`
* additions to lists and maps, and removals from them
* a token action's pulls and pushes on the input
* sends to another parser, with the parsing they caused
* any of these done in a function that an action calls

If actions send to another parser, give that parser no token actions. If the
sending parse backs up over a send to a parser with token actions, the other
parser's parse can fail. A parser that needs token actions can be fed after
the parse instead: keep what to send in a list during the parse, and send it
once the parse has ended.

Colm doesn't undo what is printed, or what is sent to any stream: `stdout`,
`stderr`, a file, or a stream made with `new stream()`. Nor does it undo a
stream's `close()` or `auto_trim()`, or an input's `auto_trim()`. An action's
local variables end with the action, and need no undoing.

A parse that fails has backed up over every action, so the data is as it was
before the parse. The exception is writes made before a `commit`. The parser
can't back up past a commit, so they stay. xref:3_02_parse.adoc#parsing[The
parsing chapter] covers `commit`.

Undoing a write puts back the value that the variable had before the write.
It doesn't reverse the change: undoing `I = I + 1`, run when `I` was 1, sets
`I` to 1, whatever `I` holds by then. So a change made from outside the parse,
after an action and before the parser backs up over it, would be lost: the
variable would get back the value it had before the action.

For lists and maps it would be worse. Backing up over an action that changed a
list or a map assumes the list or map is as the parse's actions left it:
undoing a push takes the value at that end off, undoing a pop or a `remove`
puts back what it took out, and undoing an `insert` or a `set` takes out the
key it added, or puts back the value it replaced, without looking at what the
list or map holds by then. So that it can, the parser keeps what an action's
pop or `remove` took out until the parser goes, at exit: a list or a map that
an action changes in a loop grows. A change to such a list or map from outside
the parse while the parser can still back up over the action isn't only lost:
when the parser backs up, it can corrupt the list or map, or crash the
program.

So colm doesn't compile a use of a context object from outside its parse
while a parser it is lent to can still back up, as the next section
describes.
A global has a guard of its own: where the program can run while a parser
can back up, the parser's actions can't change a global, as the section after
it describes.

[[context-lending]]
== Lending a context object

Giving a context object to a parse, or to a parser made with `new`, lends it
to the parser. While the parser can back up over its actions, the program
can't use the object at all, not even to read it. Colm checks this when it
compiles the program, and nothing is checked when it runs. The parse's own
actions use the object through the context's variables, by name, and in a
token action through `this`, as before.

A `parse` is lent its object for its statement. Its items can't use it: in
`+parse S: ctx::start( C )[ "a " C->N ]+`, the item `+C->N+` is a compile
error. After the statement the object is the program's again. The program
reads it and changes it, and gives it to another parse, which sees what the
first parse's actions left in it. A parse is given one context: colm doesn't
compile a second, with the error
`parse command requires just context and input`.

`+P: parser<ctx::start> = new parser<ctx::start>( C )+` lends `C` to the
parser in `P` until `+P->finish()+`, `+P->eof()+`, or a send to `P` that ends
with `eos`. Until then the program can't use `C`. After it, the program has
`C` back, and sends nothing more to `P`, nor finishes it again. `+P->tree+`
and `+P->error+` are read through `P` as before. While `P` is lent an object,
`+P->gets()+` is a compile error: a push onto the input it gives is a send.
Giving `P` another parser, or `nil`, ends the lend, as does the end of the
block that declares `P`: nothing can send to that parser any more.

The parser stays in `P`. Used as a value, put into another variable, passed
to a function, or kept as a send's value, as in
`+Q: parser<ctx::start> = send P "a"+`, it takes `C` with it for good: `C`
can't be used again until it is given another object. A parser made with
`new` that goes anywhere but a local variable, such as into a field or to a
function, takes its object with it the same way. A finished parser can't be
used as a value, nor can one lent what a parameter, `this`, a context's
variable or a field holds, since that can't go with it. A parser in a field
of the context gets an object of its own, as in
`+C->Inner = new parser<ctx::inner>( new ctx() )+`. The field is declared
`weak<parser<inner>>`: a parser holds its context, so a context can't hold a
parser of its own types, as
xref:2_02_list_map_struct_alias.adoc#weak[weak references] explain.
`+C->X = new parser<ctx::start>( C )+` doesn't compile: the parser takes `C`
with it, and `C` can't then be used to store it.

Putting a context object that a local variable holds into another variable,
or into a field of another context object, or returning it, moves it: the
local can't be used until it is given another object. Nothing moves out of a
parameter, which the caller lends for the call, out of `this`, or out of a
context's variable or a field, which is given another object in its place.
An iterator's parameter is lent for the whole loop, so the loop's body can't
use the object either. A function lends a parameter as if nothing else
reached its object, so a call can't give it two objects of a context that one
variable reaches, as `+f( C, C )+` and `+f( C, C->Sub )+` would, nor an
object and a parser that takes it, as
`+f( C, new parser<ctx::start>( C ) )+` would. Nor can a call give a function
that uses the context's variables one of them, or `this`.

In an action, a parse or a parser made with `new` that is given `this`, or one
of the context's variables, is lent the action's own context object. Until
the lend ends, the action can't use `this` or the context's variables, nor
call a function or an iterator that does. A `yield` runs the body of the loop
over the iterator, which can use them too. So an iterator, or a function an
iterator calls, can't yield while the context object, or one of its
parameters, is lent, nor call then a function that can yield, even in the
item of a parse.

A lend or a move on one side of an `if` holds after it. A parser finished on
one side only can't be sent to after the `if`, and keeps what it was lent. A
loop's body can't leave something from outside the loop lent, moved or
finished: the next pass would use it. What the body gives back, as `P = nil`
does, doesn't count after the loop, since the loop can end before the body
runs, or at a `break`.

Each of these is a compile error that names the object and where it was lent
or moved, such as `+cannot use C: it is lent to P (12:7) until P->finish()+`
or `+cannot use C: it went with the parser made at 9:12+`.

What the program puts into a context object through a reference to it, as
`+C->L = ...+` and `+C->L->push_tail( ... )+` do, is new: an object made with
`new`, `nil`, or something the object holds already, as in
`+Lookup->curNamespace->push_tail( Lookup->rootNamespace )+`. Anything else
could be changed through another reference while a parser can back up. Colm
stops with the error
`only a new object, nil or what C holds can go into C`.
An `int` or a `str` can come from anywhere, and so can a tree, which is copied
when it is written. But a copy of a tree shares the list, map, struct, parser
or stream that an attribute of it, or of a tree below it, holds. So a tree of
a type that can hold one there gets into a context object only through its
parse's actions. Only `nil` or what the object holds goes in this way, not
even a tree that `cons` or `parse` makes, since what makes it can give it a
list held elsewhere. Colm stops with the error
`only nil or what C holds can go into C: a T can hold a list, map, parser, stream or struct`.

Outside its parse's actions, the program reads a context object's variables,
and the lists, maps, structs and parsers they hold in place, through `+->+`,
as `+C->L->length+`, `+C->M->find( K )+` and `+C->P->tree+` do, or with a
`for` loop over values that aren't lists, maps, structs or parsers. It can't
take such a list, map, struct or parser out, where it could be changed: put it
into a variable, pass it to a function, return it, or test it, or take one out
of what a call gives, such as the struct `find` gives from a map of structs.
Colm stops with the error `cannot take L out of C, a context object`.
A tree of a type that can hold one of these counts as one too. The program
reads its attributes in place, as `+C->T.L->length+` does, and using the tree
itself as a value, even to print or match it, takes it out.

[[restartable]]
== Globals in a restartable parser

A parser is restartable when the program can run code of its own while the
parser can still back up over its actions:

* A parser made with `new parser`. The program runs between the sends to it,
  as xref:3_06_send.adoc#send[the send chapter] describes.
* A `parse` with an item after the first that runs code: a call of a
  function, a parse, a send to a parser, a parser's `+finish()+`, or a call
  that changes what it is called on, such as `+L->pop_tail()+`. A parse sends
  its items one at a time, and makes each item after it has sent the ones
  before it.
* A parse that an action of a restartable parser starts. Backing up over the
  action backs up the parse too.

Code that the program runs between sends could change a global that the
parser's actions changed, and backing up over the actions would then work on
data that isn't as they left it. So in what a restartable parser runs, its
productions' actions, the token actions and `preeof` blocks of the lex blocks
it scans with, and the functions and iterators they call, colm doesn't
compile a change to a global. A change is an assignment to the global or to a
field of a struct it holds, a write into a tree it holds, a call that changes
a list, a map or a stream it holds, such as `push_tail` or `pull`, and a send
to a parser it holds, or the parser's `+finish()+`. Colm stops with the error
`cannot change G, a global, in an action of a restartable parser: keep the data in a context`.
In a function `f` that such an action calls, the error says
`in f, which an action of a restartable parser runs` in place of
`in an action of a restartable parser`.

Nor can that code take a list, map, struct, parser or stream out of a
global, where it could be changed: put it into a variable, pass it to a
function, return it, or test it, or take one out of what a call gives, such
as the struct `find` gives from a map of structs. A copy of a tree shares the
list, map, struct, parser or stream that an attribute of it, or of a tree
below it, holds, so a tree of a type with such an attribute counts as one
too: using it as a value, even to print or match it, takes it out. That code
reads all of these in place, as `+L->length+` and, for such a tree `G`,
`+G.L->length+` do, and as `+M->find( K )+` does when the map's values aren't
any of them, or with a `for` loop over values that aren't. Colm stops with
the error
`cannot take L, a global, out in an action of a restartable parser: keep the data in a context`.
For a field of a global, the error says `cannot take L out of R, a global,
in` in place of `cannot take L, a global, out in`, and for what a call gives,
`cannot take what find gives out of M, a global, in`.

The actions can read globals, which the program can change between sends,
and send to a stream that a global holds, since what goes to a stream isn't
undone. The data they change goes in a context, as in the examples of this
chapter. The program sets up the context's object before the parse, and
uses it again once the parser it is lent to is finished.

An action that a restartable parser runs can't change a global even where a
parse that isn't restartable runs it too. A parse that isn't restartable,
such as `+parse S: start[ stdin ]+`, runs nothing else while it can back up:
its actions can change globals, and backing up undoes the changes, as it does
a context's.

xref:3_02_parse.adoc#reject[the parsing chapter] explains. With data, an

The action of `length` stores the length of a group, and starts the count.
`+counted_item*+` takes items while it can, and the action of `counted_item`
counts them. It rejects an item that the group has no room for.

Rejecting `1` as the fourth item of the first group undoes the action's
writes, including any made after the `reject`, since the rest of the action
runs. `Count` goes back to 3, so `no room for 1, count is 4` is followed by
`group of 3, count is 3`. `1` then starts the next group. The same happens to
`0` in the group of 1, and to `2` in the group of 0, which has no items.

The action of `group` rejects a group with fewer items than its length, so a
short group is a parse error. Given `3 a b`, for example, the program prints
`group of 3, count is 2`, and then a parse error at the end of the input.
