[[error-handling]]
= Error handling

Colm has no exceptions. A parse that fails gives nil, and a message that says
where the input went wrong. The program checks the result, and stops with
`exit` if it can't go on. This chapter covers telling that a parse failed, the
message in `error`, where things are in the input, stopping the program, and
the errors at run time that stop it.

[[failed-parse]]
== A failed parse

`parse` gives nil when its input doesn't form a tree of the type. The program
goes on running: a failed parse doesn't stop it, or set its exit status. So
check the result, with `if ( ! Tree )`, before using the tree. Reading a child
of the nil tree stops the program, as <<run-time-errors,the section on
errors at run time>> describes.

`error` is a `str`. Every `parse` and `parse_stop` statement sets it: to the
message when the parse fails, and to nil when it succeeds. So read it right
after the parse it belongs to. It is nil before the first parse. A parser made
with `new` keeps its message in `+P->error+`, as xref:3_06_send.adoc#send[the
chapter on send] explains.

[[message]]
== The error message

The message is `FILE:LINE:COL: parse error`. Lines and columns count from 1.
It always says `parse error`, and doesn't say what the parser expected.

It points at where the token that the parser couldn't take begins, after the
ignored text before it. In `err_check`, that is the `3` on line 3, at column 7.
Text that no token matches is pointed at where it begins. When the input ends
before the tree is whole, the message points at the end of the input, after
any ignored text there.

When the parser backs up and tries another way, as
xref:3_02_parse.adoc#backtracking[the parsing chapter] describes, the message
points at the furthest place that any of the ways reached.

`FILE` is `<stdin>` for `stdin`. For a file opened with `open`, it is the name
that `open` was given.

Text that a parse is given as strings or values has no file name. The message,
and the `file` of the tokens read from it, give a stand-in in its place. Lines
and columns in that text are counted from its start, and strings and values
that come one after another in a parse's list count as one text. Text from a
tree, as in a reparse, is counted the same way, from its own start, not from
where the tree was read.

[[locations]]
== Input locations

A token has four fields that say where it was read:

* `file`, a `str`, the name of the input, as in the message.
* `line` and `col`, the line and column it begins at, from 1.
* `pos`, its byte offset from the start of its file or text, from 0.

Literals have them too. Columns count bytes: a tab is one column, and a
character of several bytes, such as `é` in UTF-8, counts as several.

A token made in the program, with `cons`, or with `make_token` from a string
the program made, has `file` nil, and 0 in the others. One made with
`make_token` from `match_text` has the match's location, as
xref:3_01_lex.adoc#token-actions[the lexing chapter] says.

Reading a location field of a token variable that is nil stops the program,
as <<run-time-errors>> says. Check the token before reading its fields, as
the next example does with `if ( First )` before `twice` reads `First.line`.

A def has no location fields: `S.line` on a def doesn't compile. Read them
from one of its tokens, as the next example does with `S.name`. A token
variable given a def or an `il` from an `any` holds a tree that isn't a
token, and reading `data` or a location field of it stops the program, as
<<run-time-errors>> says.

[[stopping]]
== Stopping the program

`exit( N )` ends the program with the status `N`, as
xref:1_00_language_overview.adoc#exit[the language overview] says. It works
in a function, as `err_twice` shows, and in a token action or a production's
action: the parse stops there, and the program ends with that status. Use
`exit` as a statement of its own.

In a program run from a C or {cpp} host, `exit` ends the program, and the host
gets back its status and its `error`, as xref:8_01_embedding.adoc#embedding[the
embedding chapter] explains. Inside an exported function that the host called,
`exit` ends the host's process too, with the status `N`.

An `exit` reached through a call or a parse that is part of a larger
expression, such as an operand, an argument or an item of a `print`, ends the
program at once, and so does one reached through a call given a `ref` argument
other than a local variable or a parameter, such as `P.item` or a global. colm
can't unwind the stack there. What the program printed comes out, and the
process exits with the status, as `exit_hard( N )` does: a host's process ends
too. A write that fails as the streams are closed then stops the program with
status 1 instead, as <<io-errors>> says.

To fail the parse instead, and let the parser try another way, a production's
action uses `reject`, which xref:3_02_parse.adoc#reject[the parsing chapter]
covers.

[[run-time-errors]]
== Errors at run time

Some mistakes stop the program where they happen:

* popping a value or an element off a list that is empty or nil, as
  xref:2_02_list_map_struct_alias.adoc#lists[the lists section] describes;
* reading the `head`, `tail` or `top` of such a list;
* any other use of a nil list or map, such as a push, an `insert` or a read
  of its `length`, as the lists section and
  xref:2_02_list_map_struct_alias.adoc#maps[the maps section] describe;
* pushing a nil element onto a list, with `push_el`, `push_head_el` or
  `push_tail_el`, or an element that a list holds already, as the lists
  section describes;
* giving a map's `insert_el` or `detach_el` nil, `insert_el` an element that
  a map holds already, or `detach_el` one that the map doesn't hold, as
  xref:2_02_list_map_struct_alias.adoc#maps[the maps section] describes;
* setting the `key` of an element that a map holds, or a child or an
  attribute of such a key, as the maps section describes;
* backing up over an action's `insert`, `insert_el`, `detach_el` or `remove`,
  or its write to an element's `key`, when the program has moved the element
  into or out of a map since, as xref:3_04_undo.adoc#context[the context
  chapter] describes;
* reading or setting a field of a nil struct, as
  xref:2_02_list_map_struct_alias.adoc#structs[the structs section] describes,
  or the `value` or `key` of a nil list or map element, or reading such an
  element's `next` or `prev`;
* a `for` loop over a nil tree, as
  xref:1_06_iterators.adoc#iterators[the iterators chapter] describes, or
  over a nil list or map;
* a `yield` in a function that no iterator called, which the iterators
  chapter covers too;
* sending to a nil parser or stream, sending a nil stream to a parser or
  parsing from one, pushing one onto an input, or calling a function or
  reading a field of a nil parser or stream, as
  xref:3_06_send.adoc#send[the send chapter] describes;
* reading a parser's `tree` before its input has ended, as
  xref:3_06_send.adoc#send[the send chapter] describes;
* sending to a parser, or calling its `+finish()+`, while one of its actions
  or `preeof` blocks runs, or backing up over an earlier send to it then, as
  xref:3_06_send.adoc#send[the send chapter] describes;
* using a context variable outside a parse, or in a parse with no context or
  with an object of another struct as its context, as
  xref:3_04_undo.adoc#context[the context chapter] describes;
* a nil tree, or `nil`, among the items a `send`, `send_tree` or `parse`
  sends to a parser, as xref:3_06_send.adoc#send[the send chapter] describes;
* giving a parse, or a parser made with `new`, a context that is nil, as
  xref:3_04_undo.adoc#context[the context chapter] describes;
* a `match`, `require` or `switch` on a nil tree, as
  xref:3_03_match.adoc#match[the patterns chapter] describes;
* reading or setting a field of a token that is nil, such as `error.line`
  after a parse that succeeds, or reading one from a token variable that
  holds a def or an `il`, as <<locations,the input locations section>>
  describes;
* reading or setting a child or an attribute of a nil tree, as
  xref:3_02_parse.adoc#parsing[the parsing chapter] and
  xref:3_05_reduction.adoc#attributes[the attributes section] describe;
* setting a child to nil, by assigning nil to its label or by giving
  `make_tree` a nil child, or setting a child that the tree's production
  doesn't have, as xref:3_03_match.adoc#changing[the patterns chapter]
  describes;
* `make_tree` given the id of a token type or of `str` another way than
  `typeid<T>`, as xref:3_03_match.adoc#make[the patterns chapter] describes;
* a pull of more characters than an input or a stream has, of more than
  2147483647 of them, or of a negative number of them, as
  xref:3_01_lex.adoc#token-actions[the lexing chapter] and
  xref:3_06_send.adoc#send[the send chapter] describe;
* using a nil `str`: reading its `length`, joining it into a str, or giving
  it to a function that reads it, as xref:2_01_basic.adoc#str[the str
  section] describes;
* `reject` outside a production's action, in a function or an iterator
  called from the top-level code, a token action, a `preeof` block or a C or
  {cpp} host, as xref:3_02_parse.adoc#reject[the parsing chapter] describes;
* a `cast` of a nil tree or str, or of an `any` holding a tree of the other
  kind from the type it is cast to, as xref:1_02_expressions.adoc#cast[the
  expressions chapter] describes;
* reading `@N` or `@name` in a reduction action when the element has no
  location, as xref:3_05_reduction.adoc#reductions[the reductions chapter]
  describes;
* pushing nil onto an input with `push` or `push_ignore`, as
  xref:3_01_lex.adoc#token-actions[the section on token actions] describes,
  or pushing onto an input variable that is nil;
* a {cpp} host reading from a nil tree through the export header, other than
  its text, or walking one with `RepeatIter`, as
  xref:8_01_embedding.adoc#exports[the exports section] describes.

What the program printed before comes out first. Then the program prints
`fatal:` and what went wrong to `stderr`, and exits with status 1. A pop from
an empty list prints:

----
fatal: pop from an empty list
----

This is not `exit`. Nothing after the mistake runs, not even in a C or {cpp}
host: the host's process ends too, at once.

[[io-errors]]
== Read and write errors

A read or a write on a stream that the system refuses stops the program, as
the mistakes in <<run-time-errors>> do: what the program printed comes out
first, then the message, and the program exits with status 1. The message
names the stream, as `open` was given it, or `<stdin>`, `<stdout>` or
`<stderr>`, and says what the system said:

----
fatal: could not write out.txt: No space left on device
----

Reading a directory that `open` opened is such a read, and so is reading a
stream opened for writing. Sending to a stream opened for reading is such a
write. What a program sends to a stream is written out in blocks, so the
write can fail at a later `send`, at `+S->close()+`, or after the program
ends, when the streams it left open are closed. In a C or {cpp} host,
`colm_delete_program` closes them, and a write that fails there ends the
host's process too.

`stdout` and `stderr` are streams like the others: a program whose output
can't be written stops with status 1, even after its own code has ended.
When `stderr` is the stream that fails, the message is lost, but the status
is still 1. A write that fails while the program is stopping already is
ignored, and the message is the first one.
